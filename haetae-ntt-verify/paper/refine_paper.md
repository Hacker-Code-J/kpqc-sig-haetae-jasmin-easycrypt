초록

이 논문은 Jasmin 도구체인을 이용하여 NTT(Number Theoretic Transform) 구현의 안전성, 일반 상수 시간성, 추측 실행 상수 시간성을 검증하고 그 결과를 해석하는 방법을 제시한다. NTT는 격자 기반 전자서명과 암호 구현에서 핵심적인 다항식 연산이지만, 저수준 구현에서는 배열 경계 위반, 잘못된 포인터 사용, 비밀 데이터에 의존하는 분기 또는 메모리 접근이 보안상 중요한 문제가 될 수 있다. 따라서 수학적으로 올바른 NTT 알고리즘을 구현하는 것만으로는 충분하지 않으며, 실제 컴파일 대상 코드가 정의된 방식으로 실행되고 비밀 계수와 독립적인 실행 흔적을 갖는지 확인해야 한다. 본문은 Jasmin의 `jasminc -checksafety`, `jasmin-ct`, `jasmin-ct --speculative` 검사를 안전성, 일반 상수 시간(CT), 추측 실행 상수 시간(SCT)의 세 층위로 나누어 설명하고, 기록된 검사 출력이 어떤 구현 계층의 근거가 되는지 분석한다. 결론적으로 이 검증은 호출자 포인터 전제가 만족될 때 NTT 구현이 Jasmin 검사기 모델 안에서 정의된 실행과 공개 분기ㆍ주소 사용 규율을 만족함을 보이는 조건부 보증이다. 이는 기능적 정확성, 전체 암호학적 안전성, 모든 물리적ㆍ미세구조적 누출 부재를 직접 증명하는 것은 아니다.

I. 서론

NTT는 격자 기반 암호에서 다항식 곱셈을 빠르게 수행하기 위해 널리 사용되는 기본 연산이다. 특히 HAETAE와 같은 격자 기반 전자서명 구현에서는 NTT, 역 NTT, NTT 영역에서의 점별 곱셈이 전체 성능과 보안성에 직접적인 영향을 준다. 그러나 이러한 연산은 대개 C나 어셈블리 수준의 저수준 코드로 최적화되기 때문에, 알고리즘의 수학적 정확성만으로는 구현의 신뢰성을 충분히 설명할 수 없다. 예를 들어 배열 인덱스가 경계를 벗어나거나, 포인터가 잘못 정렬되거나, 비밀 다항식 계수에 따라 분기 또는 메모리 주소가 달라진다면, 기능적으로는 정상처럼 보이는 코드도 실제 실행에서는 정의되지 않은 동작이나 부채널 누출을 일으킬 수 있다.

Jasmin은 이러한 문제를 다루기 위해 설계된 저수준 암호 구현 언어이자 검증 도구체인이다. Jasmin으로 작성된 코드는 어셈블리에 가까운 제어와 성능을 제공하면서도, 타입화된 포인터, 배열 접근 규율, 안전성 검사, 상수 시간 검사와 같은 정적 분석 기능을 함께 제공한다. 본 논문에서 다루는 핵심 질문은 다음과 같다. 첫째, Jasmin으로 작성된 NTT 구현이 배열 경계와 메모리 접근 조건을 만족하는지 어떻게 확인할 수 있는가? 둘째, 다항식 계수와 같은 비밀 값이 분기 조건이나 메모리 주소에 영향을 주지 않는다는 사실을 어떻게 검사할 수 있는가? 셋째, Spectre-v1식 추측 실행 모델에서 공개 함수 진입점의 포인터를 어떻게 안전하게 다루어야 하는가?

본 논문은 이 질문에 답하기 위해 Jasmin 기반 NTT 구현을 안전성, 일반 상수 시간성, 추측 실행 상수 시간성의 세 층위로 나누어 분석한다. 안전성 검사는 프로그램이 정의된 의미론 안에서 실행되는지를 확인하고, 일반 상수 시간 검사는 비밀 데이터가 관측 가능한 제어 흐름과 주소 계산에 영향을 주지 않음을 확인한다. 추측 실행 상수 시간 검사는 여기에 더해 공개 함수가 외부에서 호출될 때 이미 잘못 예측된 실행 상태에 있을 수 있다는 보수적 가정을 반영한다. 따라서 본 논문의 목적은 NTT의 모든 수학적 정확성이나 HAETAE 전체의 암호학적 안전성을 새로 증명하는 것이 아니라, Jasmin 도구를 이용하여 저수준 NTT 구현이 안전하고 상수 시간적인 실행 규율을 따른다는 구현 계층의 근거를 제시하는 데 있다.

이 논문의 주장은 다음 범위로 한정된다. 호출자 포인터 전제가 만족된다는 조건 아래에서, 검증 대상 Jasmin NTT 구현은 첫째 Jasmin 의미론 안에서 정의된 방식으로 실행되고, 둘째 정상 실행에서 비밀 다항식 계수와 무관한 분기열과 주소열을 가지며, 셋째 Jasmin의 SCT/Spectre-v1식 검사기 모델 안에서 공개 진입점의 포인터를 안전하게 타입화한다. 이 범위를 넘어서는 기능적 정확성, HAETAE 전체 서명 방식의 암호학적 안전성, 모든 물리적ㆍ미세구조적 누출 부재는 본 논문의 결론으로 주장하지 않는다.

II.  검증 방법론

2.1 방법론 개요
다음 [그림 1]은 Jasmin을 활용한 안전성 및 상수 시간 검증 절차를 나타낸다. 검증 대상은 순방향 NTT, 역 NTT, NTT 영역 점별 곱셈을 수행하는 세 공개 루틴이며, 모든 검사는 같은 Jasmin 소스에 대해 수행한다. 즉, 안전성 검증을 위한 소스와 상수 시간 검증을 위한 소스를 따로 두지 않는다. 절차는 다음과 같이 세 단계로 진행한다.
1) “jasminc -checksafety”로 안전성 검사
2) “jasmin-ct”로 일반 상수 시간 검사
3) “jasmin-ct --speculative”로 추측 실행 검사

이하에서는 일반 상수 시간을 CT, 추측 실행 상수 시간을 SCT, 외부 ABI 경계에서 호출되는 공개 함수를 공개 래퍼라고 부른다. 세 검사는 서로 같은 성질을 반복해서 확인하는 것이 아니라 서로 다른 층위를 담당한다. 안전성 검사는 프로그램 실행이 Jasmin 의미론 안에서 정의되는지를 확인하여 이후 시간 분석의 기반을 제공한다. CT 검사는 정상 실행에서 비밀 계수가 분기 조건과 메모리 주소에 영향을 주지 않는지를 검사한다. SCT 검사는 여기에 더해 공개 래퍼가 추측 실행 상태에서 들어온 포인터를 Jasmin의 Spectre-v1식 모델 안에서 안전하게 다루는지를 확인한다. 따라서 전체 방법론은 “정의된 실행”, “정상 실행의 분기ㆍ주소 비간섭”, “추측 실행 모델에서의 공개 진입 경계”를 순서대로 쌓는 구조를 갖는다.

2.2 Jasmin 소스코드

검증 대상 소스는 [표 1]의 `ntt.jazz`이다. 이 이름은 실제 공개 진입점을 논문에서 설명하기 위해 사용한 대표 이름이며, 핵심은 해당 소스가 검사기에게 필요한 구조를 충분히 드러낸다는 데 있다. 자동화 검증을 위해서는 단순히 명령어만 실행해서는 안 된다. 소스코드가 검사기가 읽을 수 있는 형태로 반복 범위, 배열 인덱스, 포인터 형상, 테이블 접근 위치를 드러내야 한다. 즉, 검증 가능한 Jasmin 코드는 실행 결과만 올바른 코드가 아니라, 안전성과 상수 시간성을 판단하는 데 필요한 구조적 정보를 소스 수준에서 제공하는 코드여야 한다.

NTT 구현에서 핵심은 하나의 큰 반복문 안에서 단계 길이를 동적으로 바꾸는 대신, 순방향 변환에 대해 128, 64, 32, 16, 8, 4, 2, 1의 고정 길이 보조 함수를 사용하고, 역방향 변환은 그 반대 순서의 보조 함수를 활용하는 것이다. 이 구조는 안전성 검사와 상수 시간 검사 모두에 유리하다. 각 보조 함수 안에서는 반복 횟수와 인덱스 범위가 작은 정수 상수로 드러나므로, 검사기는 `rp[i]`, `rp[i + len]`, `zetas[j]`와 같은 접근이 선언된 배열 범위 안에 있는지를 더 직접적으로 확인할 수 있다. 또한 단계 번호, 블록 번호, 루프 카운터, 트위들 테이블 오프셋이 모두 공개 값의 함수로 표현되므로, 메모리 주소가 비밀 계수에 의해 바뀌지 않는다는 상수 시간 논증도 명확해진다.

따라서 `ntt.jazz`의 작성 방식은 단순한 구현 편의가 아니라 검증 방법론의 일부이다. 다항식 계수와 그 계수에서 파생된 Montgomery 곱셈 결과는 비밀 값으로 남아야 하지만, 반복 조건과 배열 주소는 공개 일정으로만 결정되어야 한다. 이 구분이 소스에 분명히 드러날 때 Jasmin 검사기는 안전성, 일반 상수 시간성, 추측 실행 상수 시간성을 각각 독립적으로 확인할 수 있다.

2.3 안전성 검사

안전성 검사는 다음 [명령어 1]과 같이 jasminc로 실행한다. 실행을 통해 [그림 2]와 같이 NTT, iNTT, 점별 곱셈 각각에 대해 `No Safety Violation`이 출력되는지를 확인한다. 이 결과는 검사기가 해당 공개 루틴에서 배열 경계 위반, 정의되지 않은 원시 연산, 잘못된 타입의 메모리 접근을 찾지 못했음을 의미한다.

[그림 2]의 안전성 검사 결과는 [코드 1]에 대해 다음 [표 2]의 증명 의무를 위반하지 않는다는 것을 나타낸다. 다만 이 결과는 조건부로 해석해야 한다. Jasmin의 타입화된 포인터는 검사기에게 “이 포인터는 256개의 32비트 원소를 갖는 다항식 배열로 사용된다”는 형상 정보를 제공한다. 따라서 검사기는 인덱스가 그 256개 원소 범위 안에 머무는지를 확인할 수 있다. 그러나 타입 표기가 외부 호출자가 넘긴 임의의 기계 주소를 실제로 할당하거나 정렬하거나 유효하게 만들어 주는 것은 아니다. 포인터가 유효한 메모리 영역을 가리키는지, 충분한 크기의 배열이 존재하는지, 쓰기 가능한 출력 영역이 제공되는지는 여전히 호출자와 ABI의 전제이다.

즉, 안전성 검사 결과는 “어떤 포인터를 넘겨도 안전하다”는 뜻이 아니다. 올바른 크기와 정렬을 갖는 다항식 영역이 주어진다는 전제 아래에서, Jasmin 소스가 그 영역 밖으로 나가지 않고 선언된 테이블과 배열을 정의된 방식으로 사용한다는 뜻이다. 이 전제가 충족되면 트위들 인자 테이블 접근, 다항식 배열 읽기와 쓰기, 그리고 몽고메리 곱셈이 구현된 `__fqmul` 호출은 검사기가 요구하는 안전성 의무를 위반하지 않는다. 따라서 안전성 검사는 이후의 상수 시간 논증이 의미를 갖기 위한 기본 실행 정의성 조건을 제공한다. 다시 말해 안전성 검사의 결론은 호출자 전제가 만족될 때 Jasmin 소스 실행이 정의된다는 주장으로 읽어야 하며, 이 정의성이 확보되어야 CT와 SCT 검사 결과도 올바른 실행 흔적에 대한 주장으로 해석될 수 있다.

2.4 일반 상수 시간 검사

일반 상수 시간 검사는 다음 [명령어 2]를 통해 실행한다. 성공 시 특별한 진단 출력이 나타나지 않을 수 있다. 다만 논문에서는 단순히 “출력이 없다”는 사실만을 근거로 삼아서는 안 된다. 중요한 것은 명령이 종료 상태 0으로 끝나고, 검사기가 공개 주석 아래에서 프로그램을 순회하는 동안 위반을 보고하지 않았다는 점이다. 이때 검사기는 비밀 값이 관측 가능한 위치로 흘러가는지를 확인한다. 여기서 관측 가능한 위치란 분기 조건, 반복 조건, 메모리 주소, 배열 인덱스와 같이 실행 시간이나 주소 흔적에 영향을 줄 수 있는 위치를 말한다.

자세한 공개 및 비밀 여부에 대한 라벨링은 [표 3]을 참고한다. [코드 1]은 256회 반복에서 ap[i]와 bp[i]를 읽고 __fqmul(a,b)를 계산한 뒤 rp[i]에 쓴다. 값 a, b, ab (mod q)은 비밀 정보여야 한다. 반면 인덱스 i와 포인터 기준 주소, 그리고 반복 횟수는 공개 데이터이다. 따라서 계수 값이 달라지더라도 실행되는 반복 횟수와 접근하는 주소 순서는 같아야 한다.

NTT 단계에서도 같은 원리가 적용된다. 각 단계에서 길이 `len`, 블록 번호 `block`, 내부 루프 카운터 `j`는 모두 공개 일정에 의해 결정된다. 순방향 NTT의 한 단계에서 접근 위치는 보통 다음과 같이 정해진다.

\[
i_0 = 2 \cdot len \cdot block + j,\qquad i_1 = i_0 + len
\]

따라서 한 버터플라이 연산은 `rp[i_0]`와 `rp[i_1]`를 읽고 쓰며, 트위들 테이블 위치도 단계 번호와 `block`의 공개 함수로 정해진다. 이때 다항식 계수는 덧셈, 뺄셈, Montgomery 곱셈에 사용되지만, 다음에 접근할 주소나 반복문의 진행 여부를 결정하지 않는다. 그러므로 공개 입력이 같고 비밀 계수만 다른 두 실행은 같은 단계 순서, 같은 반복 횟수, 같은 배열 주소열을 갖는다.

따라서 일반 상수 시간 검사의 핵심 결론은 두 실행이 같은 공개 입력을 갖고 비밀 계수만 다를 때, 같은 분기열과 같은 메모리 주소열을 갖는다는 것이다. 이 성질은 NTT의 대수적 정확성을 증명하는 것이 아니라, 비밀 계수가 관측 가능한 제어 흐름과 주소 계산에 영향을 주지 않는다는 구현 수준의 비간섭 성질을 확인하는 것이다.

2.5 추측 실행 상수 시간 검사

추측 실행 검사는 다음 [명령어 3]과 같이 실행한다. 검사기는 내부 루틴과 공개 루틴에 대해 추론한 타입을 출력한다. 이 출력은 오류 목록이 아니라, Jasmin SCT 검사기가 각 함수에 부여한 보안 타입을 보여 주는 결과이다. 결과를 해석할 때 가장 중요한 점은 포인터 자체의 보안 수준과 포인터가 가리키는 값의 보안 수준이 분리된다는 것이다.

검사 결과에서 내부 NTT 커널은 대체로 `ptr = public, val = secret` 형태로 해석된다. 이는 내부 루틴이 공개 포인터 기준 주소를 이용해 배열에 접근하지만, 그 주소에서 읽은 다항식 계수 값은 계속 비밀로 취급된다는 뜻이다. 반면 공개 래퍼는 외부 ABI 경계에서 들어오는 포인터를 `ptr = transient, val = secret`으로 받는다. 이는 함수가 호출되는 순간 CPU가 이미 잘못 예측된 실행 상태에 있을 수 있다고 Jasmin이 보수적으로 가정하기 때문이다. 공개 래퍼 내부에서 `#init_msf()`가 실행된 뒤에는 포인터 기준 주소를 공개 주소 계산에 사용할 수 있고, 결과 타입은 `ptr = public, val = secret` 형태가 된다.

[코드 3]에서 중요한 코드는 ‘_ = #init_msf()’이다. Jasmin의 `export` 함수의 시작 부분에 배치하는 작은 명령어로, 추측 실행 상수 시간 검사를 안전하게 만든다. 이는 “이 암호화 루틴이 실제로 시작되기 전에 안전하지 않은 추측 실행을 중지하고 검사기의 추측 상태를 재설정하라”라는 의미이다. 생성된 x86-64 어셈블리 코드에서 이는 함수 진입 지점의 방어 경계 역할을 한다. `#init_msf()`가 실행된 후에는 주석에 따라 코드가 포인터 주소를 일반적인 배열 접근을 위해 공개 주소로 안전하게 처리하는 동시에 해당 주소에 저장된 다항식 값은 비밀로 처리할 수 있다.

따라서 이 검사의 목적은 Jasmin의 NTT 함수에 대해 메모리 접근에는 공개 포인터를 사용하지만, 해당 주소에 저장된 다항식 값을 비밀로 유지하는지를 확인하는 것이다. 다만 이 결과는 Jasmin의 SCT/Spectre-v1식 검사기 모델 안에서의 주장이다. 모든 Spectre 변종, 캐시 교체 상태, 프리패치, 전력, 전자기파와 같은 물리적 또는 미세구조적 누출을 모두 배제한다는 뜻은 아니다. 즉, SCT 검사는 공개 진입점과 포인터 사용이 Jasmin의 추측 실행 모델에서 안전하게 타입화된다는 사실을 보여 주지만, 실제 하드웨어 전체에 대한 포괄적 부채널 보안 증명은 별도의 분석을 필요로 한다.

2.6 검증 결과 분석

기록된 안전성 로그는 세 공개 루틴 `poly_ntt_jazz`, `poly_invntt_jazz`, `poly_basemul_jazz`를 각각 분석하고 모두 `No Safety Violation`을 출력한다. 이는 순방향 NTT, 역 NTT, 점별 곱셈 루틴이 호출자 포인터 전제 아래에서 배열 경계와 원시 연산의 정의성 의무를 만족한다는 결과로 해석된다. 두 NTT 루틴의 안전성 출력에는 출력 다항식 포인터에 대응하는 메모리 이름이 나타나고, 점별 곱셈 출력에는 출력 포인터와 두 입력 포인터에 대응하는 메모리 이름이 함께 나타난다. 이 결과는 CT 검사의 전제가 되는 실행 정의성을 제공한다. 프로그램이 경계 밖 접근이나 정의되지 않은 연산을 할 수 있다면, 그 프로그램의 분기열과 주소열을 논하는 상수 시간 주장도 의미가 약해지기 때문이다.

일반 CT 로그는 종료 상태 0으로 끝나며 별도의 위반 메시지를 남기지 않는다. 이 결과는 단순히 화면 출력이 비어 있다는 뜻이 아니라, 검사기가 분기 조건, 반복 조건, 메모리 주소, 배열 인덱스에 비밀 계수가 흘러 들어가는 사례를 보고하지 않았다는 의미이다. 따라서 공개 일정이 같은 두 실행은 계수 값이 달라도 같은 제어 흐름과 같은 주소 흔적을 갖는다는 구현 수준의 근거가 된다. 이 결과는 NTT의 산술 결과가 올바른지를 보이는 것이 아니라, 산술에 사용되는 비밀 값이 관측 가능한 실행 구조를 바꾸지 않는다는 점을 보이는 것이다.

SCT 로그는 내부 커널과 공개 래퍼의 타입을 함께 보여 준다. 내부 NTT, iNTT, 점별 곱셈 커널은 `ptr = public, val = secret` 형태로 해석된다. 이는 주소 계산에는 공개 포인터가 사용되고, 해당 주소에서 읽은 다항식 계수는 비밀로 유지된다는 뜻이다. 반면 공개 래퍼 `poly_ntt_jazz`와 `poly_invntt_jazz`는 `ptr = transient, val = secret` 입력에서 `ptr = public, val = secret` 출력으로 해석된다. `poly_basemul_jazz`도 세 포인터 입력을 모두 `ptr = transient, val = secret`으로 받고, 결과를 `ptr = public, val = secret`으로 반환하는 구조를 갖는다. 이는 외부 호출 경계에서는 포인터를 보수적으로 취급하되, `#init_msf()` 이후에는 공개 주소 계산에 사용할 수 있도록 SCT 상태가 정리된다는 뜻이다. 따라서 SCT 결과는 공개 진입점의 방어 경계와 내부 커널의 공개 주소ㆍ비밀 값 규율이 서로 맞물려 있음을 보여 준다.

이 세 결과를 종합하면, 본 논문의 주장은 다음과 같이 정리된다. `ntt.jazz`로 표현한 Jasmin NTT 구현은 호출자 포인터 전제가 만족될 때 정의된 방식으로 실행되고, 일반 실행과 Jasmin SCT 모델에서 비밀 다항식 계수와 무관한 공개 분기 및 주소 사용 규율을 만족한다. 그러나 이 종합 주장은 여전히 구현 계층의 조건부 주장이다. 기능적 정확성, 전체 암호학적 안전성, 모든 물리적 부채널 부재는 이 검사 결과만으로 따라오지 않는다.

III. 결론 및 향후 연구내용

앞 절의 검증 결과를 종합하면, `ntt.jazz`로 표현한 Jasmin NTT 구현은 세 가지 구현 계층 성질을 만족한다. 첫째, 호출자 포인터가 올바른 크기와 정렬을 갖는다는 전제 아래에서 공개 루틴의 실행은 Jasmin 의미론 안에서 정의된다. 둘째, 정상 실행에서 비밀 다항식 계수는 분기 조건, 반복 조건, 메모리 주소, 배열 인덱스와 같은 관측 가능한 위치에 영향을 주지 않는다. 셋째, 공개 래퍼는 `#init_msf()`를 통해 추측 실행 경계를 설정하고, Jasmin SCT 모델 안에서 포인터 주소는 공개적으로 사용하면서도 해당 주소의 계수 값은 비밀로 유지하는 규율을 만족한다.

이 결론은 의도적으로 조건부이며 구현 계층에 한정된다. 검증 결과는 안전성, CT, SCT 검사기가 요구하는 의무를 해당 소스가 만족한다는 근거를 제공하지만, NTT가 수학적으로 올바른 변환을 계산한다는 기능적 정확성 증명이나 HAETAE 전체 서명 방식의 암호학적 안전성 증명을 직접 대체하지 않는다. 또한 SCT 결과는 Jasmin의 Spectre-v1식 검사기 모델에 대한 결과이지, 모든 물리적 또는 미세구조적 누출을 배제하는 실험적ㆍ형식적 증명은 아니다. 이러한 한계를 분명히 할 때, 본 논문의 기여는 과장된 보안 주장이 아니라 저수준 암호 구현을 검증 가능한 형태로 작성하고 그 검사 결과를 해석하는 방법론으로 자리 잡는다.

향후 연구에서는 세 가지 방향을 고려할 수 있다. 첫째, 현재의 안전성 및 상수 시간 검사를 EasyCrypt 기반 기능적 정확성 증명과 더 긴밀히 연결하여, NTT 구현이 안전하고 상수 시간일 뿐 아니라 명세된 수학적 변환과도 일치함을 구현에서 명세까지 종단 간으로 보이는 것이 필요하다. 둘째, 점별 곱셈과 전체 다항식 연산 경로까지 검증 범위를 확장하여 HAETAE 구현 전체의 신뢰 경계를 더 넓힐 수 있다. 셋째, Jasmin의 SCT 검사가 다루는 Spectre-v1식 모델을 넘어 실제 하드웨어에서의 캐시, 프리패치, 전력, 전자기파와 같은 물리적 또는 미세구조적 누출에 대해서는 별도의 분석과 실험적 평가가 필요하다. 이러한 후속 작업을 통해 Jasmin 기반 검증 결과는 저수준 암호 구현의 실질적인 신뢰성을 설명하는 더 강한 근거로 발전할 수 있다.
